## 本番で mem0 × エージェントを使うための設計のコツ

### 1. 何を覚えるかを決める
- `custom_instructions`（Memory 全体）や `add(..., prompt=...)`（呼び出し単位）で **アプリに必要な事実だけ** を抽出させる
- 雑談・一時的な情報・機微な個人情報（健康、金融、パスワード等）を溜めない方針を明文化する
- 期限のある情報は `expiration_date` を付ける（例: 「今週の予定」）

### 2. 何を思い出すかを調整する
- `top_k` は 3〜10 程度から。多すぎるとノイズになり、LLM が無関係な記憶に引っ張られる
- `threshold` は埋め込みモデルに合わせて調整（小さいモデルはスコアが低めに出る）
- `filters` のメタデータ条件で、場面ごとに必要なカテゴリだけを取り出す
- 検索クエリは「最新のユーザー発話」が基本。短すぎる発話（「それで？」など）は直前の文脈を足すと精度が上がる

### 3. 矛盾・古い記憶への対処
- mem0 2.x の `add()` は **追加専用**。事実が変わっても古い記憶は自動で消えない
- 対策: ①記憶に日付を付けてプロンプトに入れ「新しいものを優先」と指示する（本チュートリアルの方式）
  ②ツール型エージェントに `update_memory` / `delete_memory` を持たせる
  ③定期的なバッチで整理する（同じ話題の記憶を LLM でまとめ直す）
- `history()` で変更の監査ができる

### 4. レイテンシとコスト
- `add(infer=True)` は LLM を 1 回呼ぶ。**応答を返した後にバックグラウンドで保存** するとユーザー体感が速くなる
  （`MemoryChatAgent(background_store=True)` や `AsyncMemory` を使う）
- 抽出用の LLM はエージェント本体より小さいモデルでも十分なことが多い（`.env` の `MEMORY_LLM_MODEL`）
- 毎ターン検索するのが重ければ、セッション開始時に 1 回だけ検索してキャッシュする方法もある

### 5. スコープ設計
| よくある設計 | 書き方 |
|---|---|
| ユーザーごとの長期記憶 | `user_id=ユーザーID` |
| 会話セッションの短期記憶 | `user_id=..., run_id=セッションID` → 終了時に `delete_all(run_id=...)` |
| エージェントの運用ノウハウ | `agent_id=エージェント名`（user_id なし） |
| マルチテナント | `user_id` にテナント ID を含める or メタデータで分離し、**filters を必ず付ける** |

### 6. ユーザーへの透明性
- 「何を覚えているか」を見せ、修正・削除できる UI を用意する（`get_all` / `update` / `delete`）
- 退会時は `delete_all(user_id=...)`
- 記憶の出どころ（どのエージェント・どの会話か）を `metadata` に残しておく

### 7. インフラ
- 開発: ローカル Qdrant（このチュートリアル）や FAISS / Chroma
- 本番: Qdrant サーバー、pgvector、Redis、Elasticsearch など 20 以上のベクトル DB に対応
  （`vector_store.provider` を変えるだけ）
- マネージド版の **Mem0 Platform**（`from mem0 import MemoryClient`）を使うと、インフラ管理なしで同じ考え方の API が使える

### 8. 評価する
- 「覚えるべきことを覚えたか」「関係ない記憶を引いていないか」「古い情報で答えていないか」をテスト会話で確認する
- レッスン 06 のように **メモリ ON / OFF で回答を比較** するのが手軽な第一歩
